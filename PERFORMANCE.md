# Производительность на слабых ПК: ленивая подгрузка блоков

Раньше тяжёлые разделы рендерились целиком: список задач, база контрагентов,
команда, чат и блок «Последние задачи» на дашборде. На слабых машинах и
телефонах это давало заметные «подвисания» первого кадра, а чат с поллингом
и модалка задачи попадали в стартовый бандл страницы.

Теперь всё это подгружается лениво — по частям и по мере необходимости.

## Что где применяется

| Блок | Что сделано |
| --- | --- |
| Задачи (`TasksClient`) | список рисуется порциями по 25 строк, остальное — при прокрутке или по кнопке «Показать ещё»; модалка задачи вынесена в отдельный чанк и подтягивается в простое |
| Контрагенты (`CounterpartiesClient`) | таблица и мобильные карточки рисуются порциями по 30; `xlsx` для импорта по-прежнему грузится только при открытии загрузки файла |
| Команда и чат (`TeamClient`, `LazyChat`) | карточки сотрудников рисуются порциями по 8; список чатов в чате — тоже порциями по 8–10 с автодогрузкой при прокрутке; сообщения приходят страницами по 30 (кнопка «Показать более ранние»), а не всей историей сразу |
| Дашборд, «Последние задачи» (`RecentTasks`) | сервер отдаёт только верхушку списка (30 задач), клиент рисует по 6 и догружает при прокрутке |
| Отборы (`Combobox`) | вместо `<select>` — поле ввода с фильтрацией списка: вариантов может быть сколько угодно (люди, контрагенты), листать не нужно; список рисуется только при открытии |
| Чат с ИИ (`LazyAiChat`) | отдельный чанк, монтируется при подходе к экрану: настройки подключения, разбор SSE-потока, RAG-индекс по папке и вложения не попадают в стартовый бандл. Индекс строится локально и живёт в памяти вкладки |
| Все страницы группы `(app)` | `loading.tsx` показывает каркас (шапка + плитки + строки), пока сервер собирает данные |

## Как это устроено

`src/components/lazy.tsx`:

* `useProgressiveList(rows, { initial, step })` — хранит «набор строк + счётчик
  порций». При смене набора (поиск, фильтр, сортировка) порция сбрасывается
  прямо во время рендера, без лишнего эффекта. Следующая порция добавляется
  в `requestIdleCallback` внутри `startTransition`, поэтому прокрутка и ввод в
  поиск не блокируются.
* `LoadMore` — маркер в конце списка: попал в зону видимости (`rootMargin`
  240 px) → догрузка. Кнопка «Показать ещё» остаётся как ручной и доступный
  вариант. Если весь список влез в первую порцию, подпись не рисуется.
* `LazyMount` — монтирует содержимое только при подходе к экрану, до этого
  показывает скелетон (`src/components/skeletons.tsx`).

Размеры порций вынесены в пропсы: `initial`/`step` можно менять без правок
логики. Первая порция рендерится и на сервере, поэтому HTML остаётся
осмысленным и гидратация не прыгает.

## Живые обновления (SSE)

Чтобы задача, поставленная коллеге, появлялась у него сама — без F5, — в
приложении есть канал живых обновлений:

```
server action → publishLiveEvent(scope, actorId)
                        │
                        ▼
   /api/events (SSE, ReadableStream)  ──▶  LiveUpdates (в layout)
                        │                        │
                        │                        └─ router.refresh() для «своих» разделов
                        ▼
             /api/revision (страховка: опрос раз в 10 с)
```

* `src/lib/events.ts` — шина событий в памяти процесса (Set в `globalThis`,
  поэтому dev-перезагрузки и разные бандлы видят одни подписчиков).
* `src/app/api/events/route.ts` — SSE-поток: `event: update` + `data`
  `{ scope, actorId, at }`, «пинг» каждые 25 с, чтобы прокси не закрывали
  простой поток; без сессии — `401`.
* `src/app/api/revision/route.ts` — «отпечаток» данных (count + max(updated_at)
  по задачам, контрагентам и людям). Если прокси буферизует SSE, страница всё
  равно обновится при изменении отпечатка — максимум через 10 секунд.
* `src/components/LiveUpdates.tsx` — подписывается на поток, сверяет путь со
  скоупом события (`tasks`, `counterparties`, `users`) и делает
  `router.refresh()`. Защита от «шторма»: дебаунс 400 мс, не чаще раза в 2 с,
  скрытая вкладка не обновляется (догонит при возврате).
* События публикуют все мутации задач, контрагентов и сотрудников в
  `src/app/actions/*`. Чат не участвует — у него свой опрос сообщений.

Важно: шина живёт в одном процессе, поэтому при горизонтальном
масштабировании понадобится внешний брокер (Redis pub/sub) — в SQLite-режиме
приложение и так рассчитано на один инстанс.

## Чат: опрос, поиск, вложения

Чат намеренно не тянет всю историю: `GET /api/chat?peer=…&after=<id>` отдаёт
только новые сообщения, поэтому опрос раз в 3 с стоит нескольких килобайт.

* полный список запрашивается один раз при смене собеседника, дальше — только
  приращение по `after`, дубликаты отсекаются по `id`;
* переход к результату поиска грузит окно вокруг сообщения
  (`?around=<id>`, по 60 сообщений до/после), а не всю переписку; пока открыт
  фрагмент, опрос новых сообщений приостановлен;
* бейджи непрочитанного обновляет лёгкий `GET /api/chat/state` (агрегат
  `count(*) group by peer_id`) — раз в 5 с;
* поиск отправляется с дебаунсом 300 мс, ищет по нормализованным колонкам
  (`content_lower`, `name_lower`), поэтому регистр — и латиницы, и кириллицы —
  не важен;
* скрытая вкладка не опрашивает сервер: оба таймера проверяют
  `document.visibilityState`.

## Что стоит помнить

1. Ленивость — про отрисовку, а не про данные: страницы по-прежнему собирают
   список на сервере (`force-dynamic`). Если строк станут десятки тысяч,
   следующий шаг — серверная пагинация (`limit/offset`) в `src/db/repo.ts`.
2. `content-visibility: auto` не используется: списки и так ограничены
   порциями, а эффект от него нестабилен в таблицах.
3. Если меняется фильтр, счётчик порций сбрасывается — пользователь снова
   видит начало списка, а не «прыжок» в середину.
