# База данных: PostgreSQL + SQLite

CRM работает на **двух движках** с идентичным кодом приложения. Переключение не
требует изменений в страницах, экшенах или запросах.

## Как выбирается движок

| Условие | Движок |
| --- | --- |
| `DB_DIALECT=postgres` | Только PostgreSQL (`DATABASE_URL`) |
| `DB_DIALECT=sqlite` | Только SQLite (`SQLITE_PATH`, по умолчанию `./data/crm.sqlite`) |
| переменная не задана | Плавный режим: PostgreSQL, если доступен, иначе SQLite |

В режиме «auto» приложение пытается подключиться к PostgreSQL (таймаут 4 c).
Если база недоступна (или `DATABASE_URL` не задан) — молча переключается на
SQLite-файл. Схема создаётся автоматически (`create table if not exists`) на
первом запросе, отдельная миграция не нужна.

Активный движок виден:
* в сайдбаре — плашка «База данных: PostgreSQL/SQLite»;
* в `GET /api/health` → `{ ok: true, dialect: "sqlite", engine: "SQLite", target: "..." }`.

## Архитектура

```
src/db/schema.ts     — каноническая схема PostgreSQL (drizzle-kit push) + типы
src/db/dialect.ts    — DDL для обоих диалектов, пул PostgreSQL, драйвер SQLite, q()/q1()
src/db/repo.ts       — все запросы приложения (drizzle sql-шаблоны, dialect-agnostic)
src/db/index.ts      — публичная точка входа для серверного кода
```

Запросы пишутся один раз через `sql`-шаблон Drizzle: для PostgreSQL он
сериализуется в `$1, $2...` (node-postgres), для SQLite — в `?` (better-sqlite3).
Слой репозитория нормализует различия типов: `Date` из PostgreSQL приводится к
ISO-строке, `count(*)` (bigint-строка) — к числу, `date` — к `YYYY-MM-DD`.
В SQLite даты и время хранятся как ISO-8601 TEXT, поэтому сортировка и сравнение
сроков работают так же, как в PostgreSQL.

## Переход между движками

```bash
node scripts/seed.mjs              # демо-данные в активный движок (auto)
node scripts/seed.mjs --sqlite     # демо-данные сразу в SQLite
node scripts/seed.mjs --postgres   # демо-данные в PostgreSQL
node scripts/db-sync.mjs pg2sqlite # PostgreSQL -> SQLite (data/crm.sqlite)
node scripts/db-sync.mjs sqlite2pg # SQLite -> PostgreSQL
node scripts/db-sync.mjs status    # количество строк в обоих движках
```

Скрипт создаёт таблицы тем же DDL, что и приложение, переносит данные с
сохранением идентификаторов, заменяет содержимое целевой базы и выравнивает
`serial`/`auto increment` последовательности. Файл `.env` подхватывается
автоматически.

## Запуск только на SQLite

```bash
# .env
DB_DIALECT=sqlite
SQLITE_PATH=./data/crm.sqlite
# DATABASE_URL не нужен
```

Главный администратор (`admin@crm.ru` / `Admin12345`) создаётся автоматически
при первом открытии страницы входа, поэтому SQLite-инсталляция готова к работе
сразу после `npm run build && npm start`. Демо-данные добавляются командой
`node scripts/seed.mjs --sqlite`.

## Импорт контрагентов из Excel

Страница «Контрагенты» умеет загружать справочник из файла `.xlsx` / `.xls` / `.csv`
(кнопка **«Загрузить из Excel»**, доступна только администраторам).

| Столбец | Обязателен | Проверка |
| --- | --- | --- |
| `Наименование` | да | непустая строка (пробелы схлопываются) |
| `ИНН` | нет | 10 или 12 цифр; из ячейки берутся только цифры |
| `КПП` | нет | 9 цифр; ведущие нули числовой ячейки восстанавливаются |

Как это работает:

* файл читается **в браузере** (`xlsx` подключается динамически), заголовок
  ищется в первых 10 строках, синонимы принимаются («Название организации»,
  «ИНН контрагента» и т. п.). Перед загрузкой показывается предпросмотр
  с отметками «К загрузке / Дубль ИНН / Ошибка»;
* строки отправляются в server action `importCounterpartiesAction`
  (`src/app/actions/counterparties.ts`) порциями по 500 — ограничение размера
  запроса server action не мешает грузить до 5000 строк за раз;
* сервер повторно валидирует данные и **не создаёт дублей**: повтор ИНН
  внутри файла и уже существующий в базе ИНН пропускаются (галочка
  «Обновлять существующих по ИНН» вместо пропуска обновляет наименование и КПП,
  не затирая телефон, email, адрес и заметки);
* строки без ИНН добавляются всегда — сравнивать их не с чем;
* вставка идёт пакетами (`insertCounterpartiesBulk`, по 200 строк в одном
  `insert ... values (...), (...)`), поэтому одинаково работает и в SQLite,
  и в PostgreSQL. Отдельная миграция не нужна.

Разбор и проверка файла вынесены в `src/lib/counterpartyImport.ts` — модуль
изоморфный, им пользуются и браузер (предпросмотр), и server action.

## Журнал выгрузок (`task_exports`)

Экспорт закрытых задач в Excel доступен **только администраторам**
(`GET /api/tasks/export` возвращает `403` сотрудникам). Скачанные задачи
запоминаются в таблице `task_exports` (`user_id`, `task_id`, уникальная пара):

* по умолчанию в файл попадают только **новые** закрытые задачи, которые этот
  пользователь ещё не выгружал (`x-export-mode: new`);
* галочка «Выгрузить все» отправляет запрос с `?all=1` и повторно включает уже
  скачанные строки (`x-export-mode: all`);
* учёт ведётся отдельно для каждого администратора: то, что выгрузил один,
  остаётся новым для другого;
* если новых задач нет, API отвечает `409` с пояснением, а UI показывает
  подсказку вместо пустого файла.

Таблица описана в `src/db/schema.ts`, создаётся автоматически в обоих движках и
переносится скриптом `db-sync.mjs`.

## Чат: вложения, прочтения, поиск

Чат живёт в трёх таблицах, одинаково описанных в обоих движках
(`src/db/dialect.ts`) и в `src/db/schema.ts`:

* `messages` — сами сообщения; `recipient_id = null` означает общий чат.
* `message_attachments` — по одному вложению на сообщение (`message_id`,
  `name`, `mime`, `size`, `data` в base64). Лимит — 5 МБ: файлы хранятся в
  базе, поэтому её бэкап автоматически включает и переписку. Если понадобятся
  большие файлы, вложение стоит вынести в объектное хранилище (S3/MinIO), а в
  таблице оставить ключ.
* `chat_reads` — докуда дочитал каждый пользователь
  (`user_id`, `peer_id`, `last_read_id`; `peer_id = 0` — общий чат, уникальная
  пара `user_id + peer_id`). Непрочитанные = сообщения собеседника с
  `id > coalesce(last_read_id, 0)`.

Поиск по переписке не использует `lower()` в SQL: SQLite не умеет сворачивать
кириллицу в нижний регистр. Поэтому при вставке пишутся нормализованные копии
`messages.content_lower` и `message_attachments.name_lower`, а запрос делает
`like` по ним. Обе колонки добавляются миграцией `alter table ... add column`,
а `backfillMessageSearch()` при старте разово наполняет их для старых записей
(порциями по 200, не больше 20 итераций — дальше запрос уже ничего не находит).

Права на вложение проверяет `GET /api/chat/attachment/[id]`: личные файлы видят
только автор и получатель, файлы общего чата — любой авторизованный
пользователь. Картинки отдаются `inline` с `X-Content-Type-Options: nosniff`,
остальное — `attachment` с именем в `filename*=UTF-8''...`.

## Чат с ИИ: сессии, токены и лимиты

Блок `/ai` теперь тоже живёт в базе — история чатов и расход токенов привязаны
к аккаунту, а не к браузеру:

* `ai_chats` — чат пользователя: `title` (автоназвание по первому вопросу),
  `tokens_prompt` / `tokens_completion` (счётчик именно этого чата),
  `created_at` / `updated_at`.
* `ai_chat_messages` — сообщения чата: `role` (`user` / `assistant`), `content`,
  `reasoning` (размышления модели), `attachments` (JSON с именами и типами
  файлов), `tokens`, `prompt_tokens`, `completion_tokens`.
* `ai_usage_events` — журнал расхода: одна строка на ход (`prompt_tokens`,
  `completion_tokens`, `total_tokens`, `month = YYYY-MM`). По нему считаются
  месячный лимит и общий счётчик аккаунта. `chat_id` тут без внешнего ключа:
  удаление чата не должно стирать историю расхода аккаунта.
* `ai_quota_overrides` — расширение месячного лимита, которое выдаёт
  администратор: `user_id + month` уникальны, `monthly_limit` — новое значение
  на этот месяц. Роль при этом не меняется.
* `ai_rag_folders` / `ai_rag_chunks` / `ai_rag_terms` — RAG-папки: файлы,
  фрагменты по ~900 символов и обратный индекс (основа слова → фрагмент).

Индексы: `ai_chats (user_id, updated_at)`, `ai_chat_messages (chat_id)`,
`ai_usage_events (user_id, month)`, `ai_quota_overrides (user_id, month)`.
Все запросы фильтруются по `user_id` — чужой чат или папка отдают `404`.

## Особенности SQLite-драйвера

`better-sqlite3` различает выражения, возвращающие строки, и «пишущие»
(`INSERT/UPDATE/DELETE` без `RETURNING`). Слой `src/db/dialect.ts` проверяет
`statement.reader`: для чтения вызывается `all()`, для записи — `run()`.
Поэтому весь код приложения использует единый helper `q()`.

Если в логах появилось `This statement does not return data. Use run() instead`,
значит используется устаревшая копия `.next` — удалите каталог `.next` и
пересоберите проект.

## Нагрузка: выдержит ли SQLite 50 пользователей

Да — при соблюдении трёх условий: **один процесс Node.js**, **локальный диск**,
**включённый WAL** (в приложении включён по умолчанию вместе с `busy_timeout`,
`synchronous = NORMAL`, кэшем 16 МБ и ретраями на `SQLITE_BUSY`).

Замеры на этой кодовой базе (SQLite-режим, 33 задачи, 6 сотрудников, один процесс):

| Сценарий | Результат |
| --- | --- |
| Один пользователь, тёплые запросы | дашборд 26–86 мс, список задач 18–32 мс, чат-поллинг 3–5 мс |
| 50 одновременных записей в чат | 50/50 успешно, 129 мс суммарно (~2,6 мс на запись), 0 ошибок |
| 50 пользователей без пауз, 15 с | 1051 запрос, ~70 rps, 0 ошибок, p95 ≈ 1,2 с |
| Размер базы при таком объёме | ~76 КБ данных + WAL |

Латентность в третьем сценарии растёт не из-за блокировок SQLite, а потому что
все 50 виртуальных пользователей одновременно рендерят дашборд (React Server
Components). При реальном поведении (запрос раз в 10–30 секунд) нагрузка на
порядке ниже, и время ответа остаётся в пределах десятков миллисекунд.

### Ограничения, которые важно знать

1. **Только один инстанс.** SQLite — это файл. Нельзя запускать `next start` в
   нескольких процессах/контейнерах (PM2 cluster, несколько реплик) на одном
   файле: нужен единый процесс и persistent volume. Иначе — расхождения данных.
   По той же причине живые обновления интерфейса (`/api/events`, шина в памяти
   процесса) работают в пределах одного инстанса: клиенты другого инстанса
   получат изменения только страховочным опросом `/api/revision`. Подробнее —
   в `PERFORMANCE.md`.
2. **Не сетевой диск.** NFS/SMB ломают блокировки WAL. Только локальный SSD.
3. **Писатели сериализуются.** Одновременно пишет один; остальные ждут (до 5 с,
   затем короткие ретраи). Для 50 пользователей это незаметно, для сотен
   одновременных записей в чат — уже нет.
4. **Запрос блокирует event loop.** `better-sqlite3` синхронный: тяжёлый отчёт
   задержит остальные запросы. С текущими объёмами (тысячи задач) это
   несущественно; при миллионах строк и сложной аналитике — PostgreSQL.
5. **Резервные копии.** Копируйте файл вместе с `-wal`/`-shm` или используйте
   `sqlite3 data/crm.sqlite ".backup backup.sqlite"`.

### Когда переходить на PostgreSQL

* несколько инстансов приложения / горизонтальное масштабирование;
* больше ~100 одновременно активных пользователей с интенсивной записью;
* отчётность и аналитика на миллионах задач, длительные транзакции;
* требования к репликации и point-in-time recovery.

Переход не требует изменений кода: задайте `DB_DIALECT=postgres` и `DATABASE_URL`
(или уберите `DB_DIALECT` — при доступном PostgreSQL приложение выберет его
автоматически), затем перенесите данные:

```bash
node scripts/db-sync.mjs sqlite2pg
```

### Чек-лист переезда

1. Поднять PostgreSQL и прописать `DATABASE_URL` (в `.env` или окружении).
2. `node scripts/db-sync.mjs status` — показывает, что видно в обеих базах.
3. `node scripts/db-sync.mjs sqlite2pg` — создаёт схему тем же DDL, что и
   приложение, копирует все таблицы (включая `ai_*`: история чатов ИИ, расход
   токенов, квоты, RAG-индекс) и выравнивает `serial`-последовательности.
4. Переключить приложение: `DB_DIALECT=postgres` и перезапустить.
5. Проверить: `GET /api/health` → `dialect: "postgres"`, вход, задачи, чат,
   `/ai` (история и счётчики токенов), RAG-папки.
6. Настроить бэкапы: `pg_dump` вместо копирования файла SQLite.

Обратно — так же: `node scripts/db-sync.mjs pg2sqlite`.

### Почему это работает без переписывания

* Диалект-специфичен только DDL: `PG_DDL` и `SQLITE_DDL` в `src/db/dialect.ts`.
  Бизнес-код пишет запросы через drizzle `sql`-шаблоны, а `q`/`q1` сами
  подставляют `$1` для PostgreSQL и `?` для SQLite.
* Используются только конструкции, которые есть в обоих движках: `insert ...
  returning`, `on conflict do nothing`, `coalesce`, `length`, `like`, `sum`,
  `group by`, `count(distinct ...)`, `limit ?`.
* Различия типов прячет слой нормализации: `Date` из PostgreSQL → ISO-строка
  (`toIso`), `count(*)`/`sum()` (bigint/numeric-строки) → число (`toNum`),
  `date` → `YYYY-MM-DD` (`toYmd`).
* Поиск по кириллице не зависит от `lower()`: в базу пишутся готовые
  `content_lower`/`name_lower`, поэтому поведение в PostgreSQL и SQLite
  одинаковое.
* Пакетные вставки (RAG-фрагменты, термины) идут порциями: 150 файлов / 4 МБ
  текста и ~600 параметров на запрос — до лимита PostgreSQL (65 535 параметров)
  далеко.
* `scripts/db-sync.mjs` сверяет список таблиц с DDL и предупреждает, если
  появилась таблица, которой нет в переносе (иначе её данные потерялись бы
  молча).

Что может отличаться на практике (не ошибки, а нюансы): порядок сортировки
кириллицы зависит от коллации базы PostgreSQL (в SQLite — побайтовый), а очень
большие выборки на PostgreSQL стоит сопровождать индексами — они уже созданы
для внешних ключей и поиска.

### Итог

Для команды до ~50–70 человек с типичной CRM-нагрузкой SQLite подходит и
работает без ошибок; PostgreSQL включайте, когда появятся несколько инстансов,
интенсивная параллельная запись или тяжёлая аналитика.
